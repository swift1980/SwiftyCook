## Ticket 1: Wire the Shopping List view to its existing backend — ✅ Done

**Problem:** `ShoppingListController` (`swiftcookapi/Controllers/
ShoppingListController.cs`) is fully implemented — `GET/POST/DELETE
/shoppinglist` backed by `ShoppingListDto`/`ShoppingListCreateDto`
(ingredient/unit/amount, mirroring `CupboardDto`) — but `ShoppingList.vue`
is a static stub: a hardcoded `['Milk', 'Eggs', 'Bread', 'Tomatoes',
'Cheese']` array filtered client-side by a `query` prop that
`MainContent.vue`/the router never actually passes in. No Pinia store, no
API calls, no add/remove UI exist for it at all.

**Scope:**
- Add `swiftcookui/src/interfaces/shoppingList.ts`
  (`ShoppingListDto`/`ShoppingListCreateDto`) matching the backend DTOs.
- Add a `shoppingListStore.ts` Pinia store (`fetchAll`/`addItem`/
  `removeItem`), mirroring `cupboardStore.ts`'s structure exactly.
- Replace the hardcoded array in `ShoppingList.vue` with the real
  ingredient/unit/amount picker + list + remove-button UI, mirroring
  `Cupboard.vue`.
- Remove the dead `query` prop plumbing for this view if nothing else
  relies on it.

**Order:** No dependencies; can start immediately.

**Resolution:** Implemented as scoped — `interfaces/shoppingList.ts`,
`stores/shoppingListStore.ts`, and a real `ShoppingList.vue` (picker + list
+ remove). Deliberately does **not** mirror `cupboardStore`'s upsert/merge
behavior: the backend keys `ShoppingList` by an auto-increment `Id` (not by
`IngredientId` like `Cupboard`), so every "Add" appends a new row and
removal is by list-item `id` — confirmed via `ShoppingListDto`/
`ShoppingListCreateDto` and `ShoppingListController.Delete(int id)`.

## Ticket 2: Build a real Meal Planner (or explicitly descope it) — ✅ Descoped

**Problem:** `MealPlanner.vue` is the same kind of static stub as Shopping
List (hardcoded `['Breakfast: Oatmeal', 'Lunch: Salad', ...]` array,
client-side `query` filter that's never wired up) — but unlike Shopping
List, there is **no backend support at all**: no `MealPlan` entity, DTO, or
controller anywhere in `swiftcookapi`. This is reachable via the sidebar
and `/planner` route, so it currently presents as a broken/fake feature
rather than an unbuilt one.

**Scope (needs a product decision before implementation — see Order):**
- If keeping the feature: design a minimal `MealPlan` model (e.g.
  date + recipe reference), add `MealPlanController` (GET/POST/DELETE)
  + DTOs + AutoMapper entries + EF migration, then build the frontend
  store/view following the `Cupboard`/`Ingredient` pattern.
- If descoping: remove the sidebar link, route, and view rather than
  leaving a stub that looks functional but isn't.

**Order:** No dependency on other tickets. Recommend confirming
scope/priority with the user before starting, since this is net-new
backend work rather than a wiring fix like Ticket 1.

**Resolution:** Descoped per user decision — removed the `/planner` route,
the sidebar "Meal Planner" link, and `MealPlanner.vue` entirely rather than
leaving a fake stub live. Building a real Meal Planner (new domain model,
controller, migration) is left as a candidate for a future, dedicated
design session if the feature is wanted later.

## Ticket 3: Add a CI workflow (GitHub Actions) — ✅ Done

**Problem:** `REVIEW.md` (issue #5, still open per `IMPLEMENTATION_LOG.md`)
flagged that `.github/` only contains Copilot instructions/prompts — there
is no workflow to build/test on push or PR, confirmed by
`.github/workflows/` not existing. Regressions in either `swiftcookapi` or
`swiftcookui` aren't caught automatically.

**Scope:**
- Add `.github/workflows/ci.yml` running, on push/PR:
  - Backend: `dotnet build` and
    `dotnet test swiftcookapi.tests\swiftcookapi.tests.csproj`
    (currently 11/11 passing locally).
  - Frontend: `npm ci` + `npm run build` in `swiftcookui`
    (`vue-tsc --build` type-check + `vite build`, currently 0 errors).
- Depends on Ticket 4 landing first if frontend tests should also run in
  CI; otherwise this can ship with build-only frontend checks.

**Order:** No hard dependency; can start immediately (build-only). Revisit
after Ticket 4 to add a frontend test step.

**Resolution:** Implemented as `.github/workflows/ci.yml` with two jobs:
`backend` (.NET 9.0.x — `dotnet build` + `dotnet test`) and `frontend`
(Node 20.x — `npm ci`, `npm run lint`, `npm run build`), matching the
versions pinned in each service's `Dockerfile`. Triggers: `pull_request`
(any branch) + `push` to `master`. Adding `npm run lint` surfaced 60
pre-existing lint errors across the frontend (unrelated to Tickets 1/2);
these were all fixed in this session (see `IMPLEMENTATION_LOG.md`) so the
new lint step starts green rather than red-from-day-one.

## Ticket 4: Add a frontend test runner and initial store tests — ✅ Done

**Problem:** `REVIEW.md` (issue #6, still open) flagged that
`swiftcookui/package.json` has no test runner (no Vitest/Jest) or test
script — confirmed unchanged. Pinia stores (`cupboardStore`,
`recipeStore`, etc.), composables (`useNameSearch`, `useIngredientSearch`),
and API integration are entirely unverified, unlike the backend's xUnit
suite for `RecipeIngredientSearchService`.

**Scope:**
- Add Vitest + `@vue/test-utils` to `swiftcookui`, with a `test` script in
  `package.json`.
- Add initial unit tests for at least `cupboardStore.ts` and
  `useNameSearch.ts`/`useIngredientSearch.ts` (mocking the `api` service),
  as a template for future store/composable coverage.

**Order:** No dependency on Tickets 1-3, but pairs naturally with
Ticket 1 (test the new `shoppingListStore.ts` as part of this ticket or
immediately after).

**Resolution:** Added `vitest`, `@vue/test-utils`, and `happy-dom` as dev
dependencies (`@pinia/testing` was skipped — it requires Pinia >=4, but
this repo pins Pinia 3.0.x). Added a `test` script (`vitest run`) and a
`test` block in `vite.config.ts` (switched to `vitest/config`'s
`defineConfig` so Vite + Vitest config types merge cleanly under
`vue-tsc --build`). Added `src/stores/__tests__/cupboardStore.spec.ts`
(fetch/add/remove, success + error paths) and
`src/composables/__tests__/{useNameSearch,useIngredientSearch}.spec.ts`
(blank-query guard, success, 400-error passthrough, generic-error
fallback, `clear`/`loadPage` behavior for the ingredient search), all
mocking `@/services/api` per the ticket's scope — 16 tests total, all
passing. Wired `npm run test` into `.github/workflows/ci.yml`'s
`frontend` job (between lint and build) so future regressions are caught
in CI, not just locally.

## Ticket 5: Add ingredient-combination search for Cocktails

**Problem:** README's Functionality 2 ("Searching of Recipes by Ingredient
or combination of Ingredients, option for all ingredients or some
ingredients") is fully served for Recipes by the Advanced Search panel
(mandatory/optional ingredients + threshold, backed by
`/recipe/search/ingredients`). A grill-me review of this functionality
(this session) found the Cocktails view (`Cocktails.vue`) had its own,
weaker, client-side ingredient filter
(`cocktailStore.getFilteredCocktails`) with a `matchMode: 'and' | 'or'`
parameter that was **never actually wired to any UI control** — always
defaulted to `'and'` — making it dead/misleading code. That client-side
ingredient filter has been removed (this session) rather than fixed, per
user decision, leaving Cocktails with name search only and no ingredient
filtering at all.

**Scope (needs a product decision before implementation):**
- Design whether Cocktails should get the same mandatory/optional/
  threshold backend search as Recipes (new `/cocktail/search/ingredients`
  endpoint + service, mirroring `RecipeIngredientSearchService`), or a
  simpler cocktail-specific model (e.g. cocktails typically have fewer
  ingredients than dishes, so a full threshold UI may be overkill).
- If backend search is chosen: add the endpoint/service/DTOs, then wire
  an Advanced-Search-equivalent panel into the Cocktails route (currently
  hidden there — see Ticket 2/Functionality-2 grill session).
- If descoping further: no action needed; Cocktails remains name-search
  only.

**Order:** No dependency on other tickets. Recommend confirming
scope/priority with the user before starting, since this is net-new
backend work rather than a wiring fix.
